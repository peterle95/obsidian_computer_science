3.  **Function Templates vs. Polymorphism for Generality**

    *   **How they achieve generality:**
        *   **Function Templates:** Achieve generality by writing code that operates on *types as parameters*. The compiler generates specific versions of the function/class at compile time for each unique type used. This is often called **parametric polymorphism**.
        *   **Polymorphism (Virtual Functions):** Achieves generality by treating objects of different derived types through a common base class pointer or reference. The specific method called is determined at run time based on the actual object's type. This is often called **subtyping polymorphism**.

    *   **Typical Use Cases:**
        *   **Function Templates:** Best suited for generic algorithms or data structures where the *logic* is the same regardless of the data type (e.g., `std::sort`, `std::vector`, `findMin` from Exercise 1). They work well when the types involved don't necessarily share a "is-a" relationship but share common operations (like comparison, arithmetic).
        *   **Polymorphism:** Best suited for scenarios where you have a hierarchy of related types that share a common interface but implement that interface differently (e.g., a `Shape` base class with `Circle`, `Square`, `Triangle` derived classes, each with its own `draw()` method). It's about defining a common behavior for objects that are conceptually related.

    *   **Compile-time vs. Run-time Characteristics:**
        *   **Function Templates:** Resolution happens at **compile time**. The compiler "instantiates" a new version of the template for each distinct type argument. This generally leads to highly optimized code with no run-time overhead for type dispatch. However, it can lead to code bloat (larger executable size) if many different types are used.
        *   **Polymorphism:** Resolution happens at **run time** through virtual function tables (v-tables). When a virtual function is called through a base class pointer/reference, the program looks up the correct function implementation at run time. This introduces a slight run-time overhead (v-table lookup) but allows for dynamic behavior and avoids code bloat because only one version of the function exists.

    *   **When to choose one over the other:**
        *   Choose **Templates** when:
            *   The logic is identical for all types, and the types only need to support certain operations (e.g., `operator<`, `operator+`).
            *   You need maximum performance and compile-time type checking.
            *   The types don't necessarily form an inheritance hierarchy but share common syntactic requirements.
        *   Choose **Polymorphism** when:
            *   You have an inheritance hierarchy where derived classes provide different implementations for a common interface defined in the base class.
            *   You need to handle objects of different, but related, types uniformly at run time.
            *   You want to allow for extensibility (adding new derived types without modifying existing client code).
            *   You prioritize smaller code size over the absolute fastest execution for type dispatch.

    **Justification with respect to LSP:**
    The **Liskov Substitution Principle (LSP)** states that objects of a base class should be replaceable with objects of its derived classes without altering the correctness of the program. In simpler terms, if `S` is a subtype of `T`, then objects of type `T` may be replaced with objects of type `S` without breaking the client code. This means that derived classes should extend the functionality of the base class without changing its fundamental behavior or violating its contract.

    The example given: "even if `Square` introduces additional constraints (e.g., `setSide()` affecting both width and height)" directly violates LSP when `Square` inherits from `Shape` (or a `Rectangle` base class).

    Consider a `Rectangle` class with `setHeight(h)` and `setWidth(w)` methods. A client expects that if they call `setWidth(10)` and then `setHeight(5)`, the width will be 10 and the height will be 5.
    If `Square` inherits from `Rectangle`, its `setSide(s)` method (or its overridden `setHeight`/`setWidth`) would set *both* width and height to `s`.

    If a client has a `Rectangle* rect = new Square(5);` and then calls `rect->setWidth(10); rect->setHeight(5);`, the client expects a rectangle with width 10 and height 5. However, if `rect` is actually a `Square`, after `setHeight(5)`, both width and height would become 5, violating the client's expectation that `setWidth(10)`'s effect would persist independently. This change in behavior (the "additional constraint" where setting one dimension forces the other to change) means `Square` cannot be substituted for `Rectangle` without potentially altering the correctness of client code that expects independent width and height manipulation.

    Therefore, while `Square` *can* implement `calculateArea()`, its behavior regarding dimension manipulation (which affects its state and thus its area calculation in a way that differs from a generic `Shape` or `Rectangle`) prevents it from being a true Liskov substitute for a `Rectangle` if the client expects independent dimension setting. LSP implies that derived classes should strengthen (or at least maintain) invariants, not weaken or alter them in a way that breaks client expectations.
